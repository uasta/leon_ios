# 06｜后端推进大纲（按当前产品规划重排）

## 1. 文档目标

这份文档只回答一个问题：在当前版本规划下，后端最应该先支持什么，顺序怎么排，才能避免前后端各做各的。

## 2. 当前产品基线

当前对齐后的产品基线如下：

- 底部 3 个 Tab：`食材`、`推荐`、`我的`
- `食材` 与 `推荐` 可以自定义顺序
- V1 重点：
  - 食材勾选、单选 / 多选、跳转推荐
  - 手动录入、输入搜索、小票识别
  - 搜索、瀑布流推荐食谱、食谱详情
  - 登录、点赞、收藏、历史
- V2 重点：
  - 拍照识别食材
  - 识别结果打框
  - 口味偏好
  - 用户标签

这意味着：后端不能再只围绕“食材清单 + 提醒页”设计，也不能提前把主要精力放到会员、社区、语音等远期能力上。

## 3. V1 后端必须覆盖的业务域

### 3.1 食材域

- 食材 CRUD
- 食材搜索建议
- 批量写入
- 单选 / 多选后的推荐上下文传递
- 小票识别后的候选结果确认

### 3.2 菜谱与推荐域

- 推荐流
- 按关键词搜索菜谱
- 按食材生成推荐结果
- 菜谱详情

### 3.3 用户与行为域

- 登录 / 登出 / 当前用户
- 点赞
- 收藏
- 历史
- Tab 顺序偏好

## 4. 推荐推进顺序

### Phase 1：食材基础能力

先完成：

- 食材列表
- 食材新增 / 编辑 / 删除
- 搜索录入候选
- 批量创建食材

原因：

- 这是整个产品的起点
- 没有稳定食材数据，后面的推荐与历史都不成立

### Phase 2：推荐基础能力

再完成：

- 推荐流接口
- 菜谱搜索
- 菜谱详情
- 基于食材的推荐过滤

原因：

- V1 已经把“推荐”提升为主 Tab，不能再当作远期能力
- 即便早期推荐策略先简单，页面链路也必须先打通

### Phase 3：我的模块能力

接着完成：

- 登录接口对接
- 点赞
- 收藏
- 历史
- 用户偏好（Tab 顺序）

原因：

- “我的”承接账号与行为沉淀
- 这批数据也是后续口味偏好和用户标签的基础

### Phase 4：小票识别

最后补齐：

- 小票图片上传
- OCR 解析
- 候选食材结果返回

原因：

- 小票识别在 V1 里重要，但它属于食材录入效率工具
- 在食材 CRUD 和推荐链路没稳定前，先做 OCR 容易返工字段

## 5. 登录的定位

- 登录入口放在“我的”
- 登录不是使用食材和浏览推荐的前置门槛
- 登录后重点解锁：
  - 点赞 / 收藏 / 历史跨设备同步
  - Tab 顺序偏好同步
  - 后续口味偏好与用户标签沉淀

## 6. V1 不建议优先做的内容

- 拍照识别食材并打框
- 口味偏好建模
- 用户标签体系
- 社区
- 会员
- 语音能力

这些能力要么属于 V2，要么会显著抬高建模与服务复杂度。

## 7. 数据建模优先级

优先把下面几个模型定义稳定：

1. `Ingredient`
2. `Recipe`
3. `RecipeInteraction`（点赞 / 收藏 / 历史）
4. `UserPreference`
5. `ReceiptOCRCandidate`

V2 再引入：

1. `IngredientDetection`
2. `TasteProfile`
3. `UserTag`

## 8. 最稳的执行顺序

建议按下面顺序推进：

1. 先确认 `07-V1-API-设计文档-2026-04-23.md`
2. 后端先起食材域与推荐域路由
3. 前端打通“食材勾选 → 推荐页 → 食谱详情”
4. 再补我的模块的登录、点赞、收藏、历史
5. 最后接小票识别

## 9. 结论

当前最重要的不是先卷复杂 AI，也不是先把所有账号能力做满，而是先把 V1 的三条主链路跑通：

1. 录入食材
2. 用食材看推荐
3. 在我的里沉淀行为
