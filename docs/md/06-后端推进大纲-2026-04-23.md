# 06｜后端推进大纲（2026-04-23）

## 先说结论

你现在最需要做的，不是马上补某个具体接口，也不是立刻把登录/AI 接进去。

**最优先的事情是先冻结一版 MVP 的“业务对象 + 接口边界 + 前后端责任划分”。**

原因很简单：

- iOS 用户端目前已经有较完整的本地 MVP 骨架
- `php_admin` 目前还是另一个 demo 方向（认证 + tasks），没有真正进入“食材管理”领域
- 如果现在直接写后端，很容易出现“接口先做了，前端一接发现字段不对/流程不对/登录时机不对”的返工

所以正确顺序应该是：

1. 先定产品闭环
2. 再定数据模型和接口协议
3. 再开始补后端
4. 最后再接 AI 能力

## 当前项目真实状态

## iOS 用户端现状

已经具备：

- 食材列表
- 提醒页
- 设置页
- 食材新增/编辑/详情
- 预设食材管理
- 搜索、筛选、批量处理

当前本质上是：

- **本地内存数据驱动**
- **还没有真实持久化**
- **还没有真实网络层**
- **登录与同步入口还是占位**

这说明前端现在最适合继续做“产品闭环”和“接口对接准备”，而不是急着被服务端细节绑死。

## PHP 后端现状

当前 `php_admin` 已经有：

- Laravel 12 基础环境
- 用户注册/登录/登出/获取用户
- 邮箱验证链路
- Sanctum token
- `tasks` 的 CRUD demo

但当前后端**还不是这个 App 的后端**，因为核心业务对象不匹配：

- 现在 App 需要的是 `ingredients / presets / reminder settings / sync`
- 后端现在提供的是 `tasks`

所以对这个项目来说，`php_admin` 目前的价值主要是：

- 提供了可继续开发的 Laravel 基础骨架
- 提供了认证和 API 返回格式的参考

而不是可以直接拿来给 iOS 用户端接入。

## 产品与技术上的总原则

为了减少返工，建议你们坚持下面 4 条原则：

### 1. 先本地可用，再云同步

MVP 核心价值是：

- 记录食材
- 看临期提醒
- 快速处理食材

这些必须在不登录时也能成立。

### 2. 登录不是门禁，而是能力开关

登录只为这些能力服务：

- 换机迁移
- 云备份
- 多端同步
- 后续家庭共享

如果现在把登录做成前置门槛，会拖慢整个项目。

### 3. AI 不是第一里程碑

柚子负责 AI 服务没有问题，但 AI 应该建立在基础数据流已经稳定的前提上。

先有：

- 用户数据结构
- 食材状态流转
- 稳定 API

再接 AI 才不会反复改 prompt、改字段、改流程。

### 4. 后端先做“用户端必须依赖”的，不做“看起来高级”的

优先顺序应该围绕：

- 能否支撑 MVP 闭环
- 能否减少前端返工
- 能否给后续 AI 留好扩展点

而不是先去做复杂账号体系、复杂运营后台、复杂推荐系统。

## 最推荐的推进顺序

## Phase 0：冻结 MVP V1 定义

这是当前最重要的一步。

你需要先产出一份 V1 定义，明确：

- 本期必须上线的页面
- 每个页面的真实数据来源
- 哪些功能只做本地
- 哪些功能必须依赖服务端
- 哪些功能延后

### V1 建议只保留这些

- 食材列表
- 食材新增/编辑/删除/归档
- 临期/过期提醒聚合
- 预设食材
- 设置中的提醒策略
- 匿名本地使用
- 可选登录入口（不强制）

### V1 先不做

- 微信正式登录
- 手机短信正式通道
- 家庭共享
- 真正复杂的多端实时同步冲突处理
- 菜谱推荐
- 拍照识别
- AI 自动分析

## Phase 1：定义统一数据模型

先把“前端模型”和“后端模型”统一，否则后面每一步都会返工。

最少要先冻结这 4 类对象：

### 1. User

- `id`
- `nickname`
- `avatar`
- `auth_type`
- `phone`
- `wechat_unionid`
- `is_anonymous`
- `sync_enabled`

### 2. Ingredient

- `id`
- `user_id`
- `name`
- `quantity`
- `unit`
- `location`
- `purchase_date`
- `expiry_date`
- `note`
- `tags`
- `status`
- `is_archived`
- `created_at`
- `updated_at`

### 3. IngredientPreset

- `id`
- `user_id`
- `name`
- `default_unit`
- `default_location`
- `icon_type`
- `icon_value`
- `default_expiry_days`
- `tags`
- `sort_order`

### 4. ReminderSetting

- `id`
- `user_id`
- `days_before_expiry`
- `remind_time`
- `notify_expired`
- `enabled`

### 额外建议

`tags`、`location`、`status` 这类字段先尽量简单，不要一开始过度范式化。

建议：

- `location` 先用枚举字符串
- `tags` 先用 JSON 数组
- `status` 可由服务端计算，也可先由客户端根据 `expiry_date + is_archived` 推导

## Phase 2：先写接口协议，再写代码

这一阶段非常关键。

你要先整理一份“用户端 API 合同”，至少包含：

- 路径
- 方法
- 请求字段
- 响应字段
- 错误码
- 是否需要登录

### V1 最小 API 集合建议

#### 认证与账号

- `POST /api/auth/guest`
  - 创建匿名会话或匿名用户标识
- `POST /api/auth/login`
  - 先保留简单实现，后续再替换手机号/微信
- `POST /api/auth/logout`
- `GET /api/me`

#### 食材

- `GET /api/ingredients`
- `POST /api/ingredients`
- `GET /api/ingredients/{id}`
- `PUT /api/ingredients/{id}`
- `DELETE /api/ingredients/{id}`
- `POST /api/ingredients/{id}/archive`
- `POST /api/ingredients/{id}/postpone`

#### 预设

- `GET /api/presets`
- `POST /api/presets`
- `PUT /api/presets/{id}`
- `DELETE /api/presets/{id}`
- `POST /api/presets/reorder`

#### 提醒设置

- `GET /api/reminder-settings`
- `PUT /api/reminder-settings`

#### 同步

- `POST /api/sync/push`
- `GET /api/sync/pull`

如果觉得 `sync` 现在太复杂，可以先不做独立同步接口，先走标准 CRUD，等本地持久化稳了再补。

## Phase 3：先完成本地持久化，再接服务端

这是一个很容易被忽略，但实际非常关键的步骤。

当前 iOS 还是内存 store。建议先补：

- 本地持久化（SwiftData 或轻量本地存储）
- Repository 层
- Network 层抽象
- Mock API / 真 API 可切换

这样你后面接后端时，改动会集中在数据源层，而不会冲击页面层。

### 前端在这一步要完成

- `IngredientStore` 不再直接写死样例数据
- 视图只依赖 store / repository
- 登录状态、同步状态、提醒设置有明确状态机

## Phase 4：后端真正开始落地

只有在前面几步完成后，才建议正式开啃 `php_admin`。

建议后端实施顺序如下：

### 第一步：把 `tasks` 彻底换成 `ingredients`

需要补：

- migration
- model
- controller
- request validate
- resource/response format
- route

目标：

- 先把食材 CRUD 跑通
- 让 iOS 端可以接入最核心的列表/新增/编辑/删除

### 第二步：补 `presets`

原因：

- 这是你现在产品里非常核心的提效点
- 数据结构简单
- 收益高，风险低

### 第三步：补 `reminder_settings`

原因：

- 设置页会依赖它
- 推送策略以后也要依赖它

### 第四步：再看是否做云同步

如果当前只有你一个前端开发，建议先不要上来做复杂同步。

更现实的方式是：

- 登录后先从服务端拉取
- 本地改动后直接写服务端
- 冲突先采用“最后写入覆盖”

这已经足够支撑 MVP。

## Phase 5：AI 服务最后接

AI 服务应该建立在食材数据稳定之后。

推荐顺序：

### AI V1 只做一个能力

- 基于现有食材列表生成“优先消耗建议”

例如输出：

- 今天优先吃什么
- 哪些食材快过期
- 两三个简单做法建议

### 为什么先只做这个

- 直接贴近核心价值
- 不依赖复杂图片识别
- 不依赖复杂菜谱系统
- 前后端接口简单

### AI 接口建议

- `POST /api/ai/ingredient-insights`

输入：

- 当前食材列表
- 用户偏好（可选）

输出：

- 临期优先级
- 消耗建议
- 简单做法建议

等这条链跑顺，再扩展：

- 菜谱推荐
- 拍照识别
- 智能入库

## 你和柚子的分工建议

## 你负责

你现在不只是前端，也要临时承担产品和技术 owner 的角色。

你应该优先抓这几件事：

### 1. 冻结 V1 产品范围

你来拍板：

- 哪些功能一定做
- 哪些功能延后
- 登录在什么时候触发
- AI 本期是不是只做一个能力

### 2. 冻结前后端数据契约

你来定义：

- Ingredient 字段
- Preset 字段
- ReminderSetting 字段
- 接口返回格式

### 3. 完成 iOS 端“可接后端”的架构准备

你来推进：

- 本地持久化
- Repository 抽象
- 网络层抽象
- Mock/Real API 切换

## 柚子负责

柚子更适合在你把基础数据结构定下来之后进入。

建议柚子先接这两块：

### 1. AI 服务输入输出协议

不是先写模型能力，而是先约定：

- 输入需要哪些字段
- 输出 JSON 长什么样
- 哪些文案由 AI 返回
- 哪些字段必须结构化

### 2. AI V1 单点能力落地

建议先只做：

- 临期食材分析
- 优先消耗建议

不要一开始同时做：

- 图片识别
- 菜谱生成
- 采购建议

## 你现在这一周最应该做什么

如果只看“当前最重要”的事情，我建议你按这个顺序执行：

### Day 1：写清楚 V1

产出一个 1 页文档，明确：

- V1 功能范围
- 延后项
- 登录策略
- AI 范围

### Day 2：冻结接口和数据结构

产出：

- `Ingredient`
- `IngredientPreset`
- `ReminderSetting`
- API 列表
- 错误码与返回结构

### Day 3-4：先改 iOS 架构

目标：

- 从“内存样例数据”升级到“本地持久化 + 可替换数据源”

### Day 5-7：开始改 PHP 后端

先做：

- `ingredients`
- `presets`
- `reminder_settings`

不要先做：

- 微信登录
- 短信通道
- AI 接口大而全

## 最后给你的判断

如果站在产品 owner 和开发 owner 两个视角一起看：

**你现在最需要做的事情只有一句话：先把用户端 MVP 的数据契约定死。**

不是先卷 UI，不是先卷 AI，不是先卷登录。

因为一旦这个契约稳定：

- 你前端能放心重构本地持久化
- 我可以顺着这个契约补 PHP 后端
- 柚子可以基于稳定数据接 AI 服务

整个项目才会真正进入“可持续推进”的状态。

## 下一步建议

最推荐立刻开始的两件事：

1. 先补一份 `V1 API 设计文档`
2. 再把 iOS 的 store 改造成“本地持久化 + repository”

这两步做完，后端就可以开始高效落地，而且返工会少很多。
