# 07｜V1 API 设计文档（用户端）

## 1. 文档目标

这份文档只服务当前 iOS 用户端 V1。

目标不是把后端一次设计到很大，而是先让下面三件事完全对齐：

- 当前前端已有页面到底需要什么数据
- `php_admin` 下一步该补哪些真实业务接口
- 产品、客户端、服务端在 V1 阶段各自负责什么

---

## 2. 当前产品现状

当前用户端已经存在这些核心页面：

- 食材列表页
- 食材详情页
- 新增/编辑食材 Sheet
- 提醒页
- 预设管理页
- 设置页
- 登录占位页

当前后端 `php_admin` 已有：

- 注册 / 登录 / 登出 / 当前用户
- 邮箱验证
- `tasks` CRUD 示例

结论：

- iOS 端已经接近“产品骨架完成”
- 后端还没有进入“食材管理”业务域
- 所以 V1 API 必须以 iOS 现有页面为准重新定义

---

## 3. V1 范围

### 3.1 V1 必做

- 匿名模式可用
- 登录后可绑定到账号
- 食材增删改查
- 食材归档
- 食材筛选与搜索
- 临期 / 过期聚合
- 常用预设管理
- 提醒设置读取与修改

### 3.2 V1 不做

- 微信正式登录
- 手机号验证码正式通道
- 家庭共享
- 多人协作
- 复杂同步冲突解决
- AI 推荐 / 拍照识别 / 菜谱推荐

---

## 4. 设计原则

### 4.1 登录不是门禁

- 用户不登录也能完成记录、查看、处理食材
- 登录只在“同步 / 迁移 / 备份”场景触发

### 4.2 先做资源型 API，再谈高级同步

- V1 优先保证客户端能稳定拉取和提交数据
- 同步先做“全量拉取 + 时间戳增量”的简化模式

### 4.3 服务端字段要贴合当前前端模型

当前前端核心模型已经非常明确：

- `Ingredient`
- `IngredientPreset`
- `ReminderSetting`
- `UserSession`

后端不应继续围绕 `Task` 设计接口。

---

## 5. 统一返回格式

所有 V1 API 统一返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

约定：

- `code = 0` 表示成功
- 非 0 表示业务失败
- 参数校验失败使用 HTTP `422`
- 未登录使用 HTTP `401`
- 无权限使用 HTTP `403`
- 资源不存在使用 HTTP `404`

---

## 6. 认证策略

### 6.1 V1 推荐状态

- `anonymous`：匿名本地模式
- `authenticated`：已登录，可同步

### 6.2 Token 方案

- 服务端沿用 `Sanctum`
- iOS 登录后持有 `Bearer Token`
- 本地匿名数据不依赖服务端 token

### 6.3 V1 认证接口

保留现有接口，但语义要从“邮箱 demo”逐步过渡到“用户端登录能力”：

- `POST /api/register`
- `POST /api/login`
- `POST /api/logout`
- `GET /api/user`
- `POST /api/resend-verification`

说明：

- 这一批接口短期可继续保留邮箱登录
- 但在产品层面，它们属于“开启同步能力”的入口，不应成为首页强依赖

## 7. 核心资源模型

## 7.1 Ingredient

```json
{
  "id": "ing_123",
  "name": "番茄",
  "quantity": 4,
  "unit": "个",
  "location": "fridgeChill",
  "purchase_date": "2026-04-20",
  "expiry_date": "2026-04-24",
  "note": "适合先吃",
  "tags": ["蔬菜"],
  "is_archived": false,
  "freshness": "expiringSoon",
  "days_left": 1,
  "created_at": "2026-04-23T08:30:00Z",
  "updated_at": "2026-04-23T08:30:00Z"
}
```

字段说明：

- `location`：`fridgeChill | fridgeFreeze | pantry | other`
- `freshness`：服务端返回，减少多端重复计算
- `days_left`：用于提醒页和列表状态展示
- `tags`：V1 直接存 JSON 数组即可

## 7.2 IngredientPreset

```json
{
  "id": "preset_001",
  "name": "鸡蛋",
  "default_unit": "枚",
  "default_location": "fridgeChill",
  "default_expiry_days": 14,
  "icon_type": "system",
  "icon_value": "circle.hexagongrid.fill",
  "tags": ["蛋奶"],
  "sort_order": 1,
  "created_at": "2026-04-23T08:30:00Z",
  "updated_at": "2026-04-23T08:30:00Z"
}
```

## 7.3 ReminderSetting

```json
{
  "days_before_expiry": 2,
  "remind_time": "09:00",
  "notify_expired": true,
  "enabled": true,
  "updated_at": "2026-04-23T08:30:00Z"
}
```

## 7.4 SyncStatus

```json
{
  "mode": "anonymous",
  "sync_enabled": false,
  "last_sync_at": null
}
```

## 8. 页面到 API 的映射

| 页面 | 读取接口 | 写入接口 |
| --- | --- | --- |
| 食材列表 | `GET /api/v1/ingredients` | `POST /api/v1/ingredients` |
| 食材详情 | `GET /api/v1/ingredients/{id}` | `PATCH /api/v1/ingredients/{id}` |
| 食材快捷操作 | 无额外读取 | `POST /api/v1/ingredients/{id}/archive` `POST /api/v1/ingredients/{id}/postpone` |
| 提醒页 | `GET /api/v1/reminders/summary` | 复用食材归档/延期接口 |
| 预设管理 | `GET /api/v1/presets` | `POST/PATCH/DELETE /api/v1/presets/*` |
| 设置页 | `GET /api/v1/settings/reminders` | `PUT /api/v1/settings/reminders` |
| 登录后同步状态 | `GET /api/v1/sync/status` | `POST /api/v1/sync/bootstrap` |

## 9. V1 API 清单

## 9.1 食材接口

### 9.1.1 获取食材列表

`GET /api/v1/ingredients`

查询参数：

- `keyword`：搜索名称 / 标签
- `location`：按位置筛选
- `freshness`：`fresh | expiringSoon | expired | noExpiry`
- `archived`：`true | false`
- `tag`：标签筛选
- `page` / `per_page`

响应示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "pagination": {
      "page": 1,
      "per_page": 20,
      "total": 0
    }
  }
}
```

### 9.1.2 创建食材

`POST /api/v1/ingredients`

请求体：

```json
{
  "name": "番茄",
  "quantity": 4,
  "unit": "个",
  "location": "fridgeChill",
  "expiry_date": "2026-04-24",
  "note": "先吃",
  "tags": ["蔬菜"]
}
```

### 9.1.3 获取食材详情

`GET /api/v1/ingredients/{id}`

### 9.1.4 编辑食材

`PATCH /api/v1/ingredients/{id}`

支持部分更新字段：

- `name`
- `quantity`
- `unit`
- `location`
- `purchase_date`
- `expiry_date`
- `note`
- `tags`
- `is_archived`

### 9.1.5 删除食材

`DELETE /api/v1/ingredients/{id}`

### 9.1.6 归档食材

`POST /api/v1/ingredients/{id}/archive`

请求体：

```json
{
  "is_archived": true
}
```

说明：

- 对应当前前端里的“用掉 / 标记为已用完”
- 单独拆接口比强依赖通用 `PATCH` 更清晰

### 9.1.7 延期食材

`POST /api/v1/ingredients/{id}/postpone`

请求体：

```json
{
  "days": 1
}
```

说明：

- 对应当前提醒页和列表页里的“延期 1 天”

## 9.2 提醒接口

### 9.2.1 获取提醒汇总

`GET /api/v1/reminders/summary`

响应建议：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "expiring_soon": [],
    "expired": [],
    "stats": {
      "expiring_soon_count": 2,
      "expired_count": 1
    }
  }
}
```

说明：

- 该接口主要服务提醒页
- 即使底层仍基于 `ingredients` 查询，前端层也值得有一个聚合接口

---

## 9.3 预设接口

### 9.3.1 获取预设列表

`GET /api/v1/presets`

### 9.3.2 创建预设

`POST /api/v1/presets`

请求体：

```json
{
  "name": "鸡蛋",
  "default_unit": "枚",
  "default_location": "fridgeChill",
  "default_expiry_days": 14,
  "icon_type": "system",
  "icon_value": "circle.hexagongrid.fill",
  "tags": ["蛋奶"]
}
```

### 9.3.3 更新预设

`PATCH /api/v1/presets/{id}`

### 9.3.4 删除预设

`DELETE /api/v1/presets/{id}`

### 9.3.5 调整预设顺序

`POST /api/v1/presets/reorder`

请求体：

```json
{
  "ids": ["preset_003", "preset_001", "preset_002"]
}
```

说明：

- 对应当前前端 `onMove`
- 这个接口很重要，否则排序会在多端间不一致

### 9.4.2 更新提醒设置

请求体：

```json
{
  "days_before_expiry": 2,
  "remind_time": "09:00",
  "notify_expired": true,
  "enabled": true

```

---

## 9.5 同步接口

### 9.5.1 获取同步状态

`GET /api/v1/sync/status`

### 9.5.2 首次登录后的本机数据上云

`POST /api/v1/sync/bootstrap`

请求体：

```json
{
  "ingredients": [],
  "presets": [],
  "reminder_setting": {
    "days_before_expiry": 2,
    "remind_time": "09:00",
    "notify_expired": true,
    "enabled": true
  },
  "strategy": "merge_local_first"
}
```

说明：

- 这个接口解决“用户先匿名使用，后登录”的现实问题
- 推荐 V1 默认策略：以本机数据为主，首次上云

## 10. 客户端状态建议

客户端至少维护以下状态：

- `authStatus`：匿名 / 已登录
- `syncStatus`：关闭 / 同步中 / 成功 / 失败
- `ingredients`
- `presets`
- `reminderSetting`
- `lastSyncAt`

说明：

- 即便接入服务端，客户端仍应保留本地缓存
- 不要把 V1 做成“纯在线才可用”

---

## 11. 服务端实现优先级

建议 `php_admin` 按下面顺序推进：

1. 保留现有认证接口，先不大改
2. 新建 `ingredients` 相关 migration / model / controller / routes
3. 新建 `presets` 相关 migration / model / controller / routes
4. 新建 `reminder_settings` 相关表与接口
5. 增加 `sync/bootstrap` 接口
6. 最后清理 `tasks` demo 与旧 `openapi.json`

---

## 12. 与当前代码的差距

当前 iOS 端已经体现出的真实需求：

- 食材位置枚举
- 标签数组
- 到期日驱动的 freshness
- 归档
- 延期
- 预设排序

当前 `php_admin` 尚未体现：

- 食材领域模型
- 预设领域模型
- 提醒设置
- 匿名转登录的数据迁移

这意味着：

- 现在最适合先按本文件补后端骨架
- 不适合直接把现有 `tasks` CRUD 改名后强行复用
