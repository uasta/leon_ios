# 01｜登录与账号体系（手机号 + 微信授权）

## 结论（推荐）

对“食材管理”这种工具型 App，国内场景下更推荐：

- **默认不强制登录**（本地即可用）  
- **在需要云能力时再引导登录**：跨设备同步 / 更换手机迁移 / 点赞收藏历史同步 / 数据备份

这样能最大化“先感知价值”，降低首次打开的流失。

## 为什么不建议一进入就强制登录

- **用户此刻的目标是“赶紧记录”**，强制登录会打断节奏
- 手机号验证码链路受网络/短信通道影响，失败体验会被放大
- 微信授权在 iOS 上也会遇到未装微信/跳转失败等边界

> 只有在你的产品强依赖云端时才建议强制登录。

## 账号体系目标

- **可用**：不登录也能完成完整的本地闭环
- **可迁移**：一键把本地数据迁移到云端账号
- **可合并**：手机号与微信绑定后能合并为同一账号（避免“双号”）

## 登录方式设计

### 手机号登录/注册（验证码）

- **适用**：最通用、适合“迁移/绑定”场景
- **关键点**：
  - 明确提示：仅用于同步/备份，不会骚扰
  - 失败兜底：收不到验证码的提示与重试节奏
  - 风控提示：验证码频率限制与文案（不要生硬）

### 微信授权登录

- **适用**：微信重度用户、希望“更快一步完成登录”
- **关键点**：
  - 未安装微信时：给出“用手机号登录”的替代入口
  - 授权失败：回到登录页，不要卡死在空白页
  - 授权信息最小化：默认只拿到 openid/unionid 级别即可

## 何时触发登录（具体触发点）

把登录做成“能力开关”，而不是“门禁”：

- **触发点 A：开启云同步**（我的页中的设置入口）
- **触发点 B：更换手机/导入导出**（引导页）
- **触发点 C：同步点赞/收藏/历史**（进入“我的”后触发）

## 引导文案与信息层级（iOS 风格）

- 弹窗/底部卡片第一句话只讲**收益**：  
  - “登录后可自动备份，换手机也不丢。”
- 第二句话讲**成本**：  
  - “仅需 10 秒完成验证。”
- 永远提供**稍后再说**（除非触发点本身就必须登录，比如立即同步到账号）

## 本地数据与账号数据的关系（强烈建议）

- **匿名模式**：数据只在本机（Keychain/本地数据库）
- **登录后**：提供“将本机数据上传到账号”的一步式迁移
- **合并策略（简化版）**：
  - 以“本机数据”为主，首次登录时上传覆盖空账号
  - 若账号已有数据：提供两按钮  
    - “合并（推荐）”  
    - “用云端覆盖本机”

## 最小可行接口/状态（用于后续落地）

- 登录状态：`anonymous` / `authenticated`
- 账号绑定状态：`phoneBound` / `wechatBound`
- 同步状态：`off` / `on` / `syncing` / `error`
