# 01｜登录与账号体系（当前：邮箱密码）

## 结论（当前版本）

对“食材管理”这种工具型 App：

- **默认不强制登录**（本地即可用）
- **在需要云能力时再引导登录**：跨设备同步 / 点赞收藏历史同步 / 数据备份
- **1.0 登录方式固定为邮箱 + 密码**（含邮箱验证）
- **手机号验证码、微信授权暂缓**，不纳入当前 1.0 收尾范围

这样能最大化“先感知价值”，同时把账号能力收敛到现有已打通的邮箱链路，降低实现与联调成本。

## 为什么不建议一进入就强制登录

- **用户此刻的目标是“赶紧记录”**，强制登录会打断节奏
- 验证邮件、网络失败等边界体验会被放大
- 只有在产品强依赖云端时才建议强制登录

## 账号体系目标（1.0）

- **可用**：不登录也能完成完整的本地闭环
- **可登录**：邮箱注册 → 邮件验证 → 登录拿 Token → 会话恢复 → 登出
- **可补救**：未收到验证邮件可重发；忘记密码可重置（收尾项）
- **可迁移**：登录后把本机食材等数据同步到账号（已有 bootstrap 基础）

暂缓目标（不进当前迭代）：

- 手机号 OTP 登录 / 注册
- 微信授权登录
- 手机号与微信的账号绑定 / 合并

## 登录方式设计（当前）

### 邮箱注册 / 登录（主路径）

- **适用**：当前联调与 1.0 发布主方案
- **关键点**：
  - 注册后必须完成邮箱验证才能登录
  - 提供「重新发送验证邮件」与清晰的「去登录」引导
  - 登录失败、未验证、密码错误等错误语义要对用户可读
  - Token 失效时统一清会话并引导重新登录

### 暂缓：手机号 / 微信

- 国内长期形态仍可能回到手机号 + 微信，但依赖短信通道、微信开放平台与 iOS 配置，成本高
- **决策**：先把邮箱链路做稳，再评估是否引入第三方登录
- Settings 等处的微信 / 手机号占位 UI，视为未实现入口，不作为 1.0 交付项

## 何时触发登录（具体触发点）

把登录做成“能力开关”，而不是“门禁”：

- **触发点 A：开启云同步**（我的页中的设置入口）
- **触发点 B：同步点赞 / 收藏 / 历史**（进入“我的”或详情操作时）
- **触发点 C：需要账号态的其他云能力**

## 引导文案与信息层级（iOS 风格）

- 弹窗 / 底部卡片第一句话只讲**收益**：
  - “登录后可自动备份，换手机也不丢。”
- 第二句话讲**成本**：
  - “使用邮箱完成验证即可。”
- 永远提供**稍后再说**（除非触发点本身就必须登录）

## 本地数据与账号数据的关系

- **匿名模式**：数据只在本机
- **登录后**：通过同步把本机数据上传到账号
- **合并策略（简化版）**：
  - 以“本机数据”为主，首次登录时上传覆盖空账号
  - 若账号已有数据：后续再提供「合并」与「用云端覆盖本机」

## 1.0 登录收尾优先级

按垂直切片推进（前后端同步，优先打通可用链路）：

1. **重发验证邮件 + 注册后引导登录**（已落地）
2. **Token 失效统一处理**（已落地：401 清本地 token 并回匿名态）
3. **表单校验加强**（邮箱格式已有基础校验；字段级错误可继续加强）
4. **忘记 / 重置密码**（已落地：App 申请 + 邮件网页重置）
5. **登录后同步结果提示**（成功 / 失败可读反馈，待加强）

## 最小可行状态（当前落地）

- 登录状态：`anonymous` / `authenticated`
- 同步状态：`off` / `on` / `syncing` / `error`
- 账号标识：邮箱（已验证后可登录）
